# アーキテクチャ

## 設計の中心にある1つの判断

**推論は描画より遅い。それを前提に組む。**

深度推定は 7〜18 ms、描画は 7 ms。同じスレッドで回せば絵が推論に引きずられる。
だから:

  * 取り込みは専用スレッドで回し、**最新の1枚だけ**を保持する (キューに溜めない)
  * 深度推論も専用スレッド。`submit()` は最新フレームで上書きするだけ。
    間に合わない入力フレームは黙って捨てる
  * `latest()` は「前回より新しい結果」があるときだけ返す。無ければ描画は
    **前回の深度マップを使い続ける**
  * フローだけはメインスレッドで同期実行する。筆の向きを直接駆動するので
    遅延が体験に出やすく、かつ 5〜8 ms と軽い

結果として深度の場が 26 Hz でしか更新できなくても、絵は 130 fps で動く。
「捨てたフレーム数」を終了時に出しているのは、この設計が実際に効いていることの証跡。

```
┌─ 取り込みスレッド ───────────────┐
│ VideoCapture → flip → BGR2RGB     │
│ → 最新1枚を lock 下で差し替え     │
└───────────────┬───────────────────┘
                │ latest() は (frame, 取り込み時刻, 連番)
┌─ メインスレッド ─────────────────┴────────────────────────────┐
│ 連番が変わっていたら:                                          │
│   ・カメラテクスチャ更新 + mipmap 生成                          │
│   ・Farneback フロー (320x180) → RG16F テクスチャ               │
│   ・深度ワーカへ submit                                        │
│ 深度の新しい結果があれば R16F テクスチャ更新                   │
│ uAdv += gust(t) * (0.30 + 2.5*energy) * dt                     │
│ brush.frag を内部解像度 FBO へ → present.frag でウィンドウへ    │
│ e2e レイテンシ = 現在時刻 − そのフレームの取り込み時刻          │
└──────────────┬────────────────────────────────────────────────┘
               │ submit() は上書き / dropped++
┌─ 推論スレッド ┴──────────────────────────────────────────────┐
│ preprocess (GPU resize + 正規化) → forward → 読み戻し          │
│ → DepthNormalizer (非対称EMA) → 結果を差し替え + seq++          │
└───────────────────────────────────────────────────────────────┘
```

## レイテンシ予算 (1280x720, 合成入力, 全エフェクト有効)

| 段 | teacher | student |
|---|---|---|
| フロー (メインスレッド, 同期) | 7.4 ms | 7.6 ms |
| 深度推論 (別スレッド, 描画とGPU共有) | 35.0 ms | 22.6 ms |
| 描画 1 フレーム | 18.9 ms (52.9 fps) | 7.4 ms (134.6 fps) |
| **end-to-end (取り込み→表示)** | **36.3 ms** | **22.2 ms** |

深度推論の数字が単体計測 (17.9 / 7.0 ms) より大きいのは、描画と GPU を共有しているため。
**単体のベンチだけ見ていると、モデルを重くしたときに絵が遅くなる理由が説明できない。**

## 内部解像度の FBO を挟む理由

筆触パスは 1 フラグメントあたり

  * 5x5 = 25 個の楕円を探索して1枚を勝たせる (`hash21` を複数回)
  * 24 枚の花びらをループ (`exp` と回転)
  * `fbm2` (4 オクターブの value noise) を複数回

を回す。Retina のフレームバッファ (2560x1440) で直接描くと画素数が 4 倍になる。
筆のサイズは正規化座標で決まるので**内部解像度を変えても筆の大きさは変わらない**
(変わるのは鮮明さだけ)。加えてスクリーンショットがウィンドウ倍率に依存しなくなる。

## カメラテクスチャの mipmap

一筆は楕円の**中心 1 点しかサンプルしない**。フル解像度から拾うと写真の高周波が
そのままノイズとして絵に出る。`textureLod` で「一筆が覆う面積」相当の mip から読む。

```glsl
float lod = uCamLod + log2(max(szG, 0.25));   // szG は depth 由来の筆サイズ
col = scenePainterly(qc, t, lod);
```

手前の大きい筆はより粗い mip、奥の細い筆は細かい mip から読むので、
筆のサイズと情報量が自動的に釣り合う。

## 座標系の約束 (ここを間違えると全部ずれる)

| | 向き |
|---|---|
| シェーダの `q` | 0..1、**y は上向き** (GL 流儀) |
| OpenCV 由来のテクスチャ | y は下向き → `img(q) = vec2(q.x, 1.0 - q.y)` で反転して読む |
| フローの y 成分 | 画像座標では下が正 → `flowAt()` で符号を反転 |
| 深度の値 | **0 = 遠 / 1 = 近** に正規化 (単眼深度の生出力は相対逆深度なので向きが揃っている) |

カメラは取り込みスレッドで左右反転している (自撮り像)。フロー場も一緒に鏡像化されるので
後段で辻褄が合う。

## フローの単位

「画面を 1 とした**毎秒**の移動量」。フレームあたりで持つと、同じ物理的な動きでも
30 fps と 120 fps で風速が 4 倍変わる。解像度にもフレームレートにも依存しない量にして
初めて絵の挙動が再現可能になる。

空間ブラー (σ=3 @ 320x180) と時間 EMA (α=0.4) は**見た目の好みではなくレンダラの
要求仕様**。筆触パスは各フラグメントで格子ごと回転させるため、角度の場がガタつくと
格子が破れて絵が壊れる。

## 筆の向きの合成

向きは「方向」ではなく「軸」(180度回しても同じ筆)。角度を直接 `mix` すると ±π で破綻する。
2倍角ベクトルで補間する (構造テンソルと同じ考え方):

```glsl
float mixOrient(float a, float b, float w){
  vec2 va = vec2(cos(2.0*a), sin(2.0*a));
  vec2 vb = vec2(cos(2.0*b), sin(2.0*b));
  vec2 v  = mix(va, vb, w);
  return 0.5*atan(v.y, v.x);
}
```

合成する2つの場:

  * **動きの場** — フローが強い所はフロー方向に沿った筆 (動きをなぞる)
  * **形の場** — フローが弱い所は深度勾配に直交する方向、つまり等深線に沿った筆 (形をなぞる)

止まっている部分の筆も意味を持つ、というのがこの設計の狙い。

## 深度オクルージョン

花びら 1 枚ごとに深度 `pd` を持たせ、その画素のシーン深度と比較する。

```glsl
float pd  = clamp(uSeedDepth + (h1 - 0.5)*0.50 - 0.10*pr, 0.0, 1.0);
float vis = smoothstep(pd + 0.06, pd - 0.06, sceneD);   // sceneD > pd なら隠れる
```

発生点 (動きの重心) の深度を中心に **±0.25 散らす**のが要点。半分を人物より手前、
半分を奥に置くことで、シルエットの境界で「回り込み」が読める。全部同じ深度にすると
一斉に見えるか一斉に隠れるかのどちらかになり、オクルージョンだと分からない。

`smoothstep` の ±0.06 の幅は、深度マップが低解像度で境界が甘いことへの対処。
ハード比較にすると輪郭がジャギる。
