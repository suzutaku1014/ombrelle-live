# 開発ログ — 踏んだ地雷と、そこから学んだこと

初日 (2026-07-30) に M0〜M6 を一気に通し、実写を初めて通すまでの記録。
「動いた」ことより「何を間違えて、なぜそうなっていたか」を残す。

---

## 1. macOS の desktop GLSL には `noise2` が既にある

原典は WebGL (GLSL ES) で書かれていて、そこには `noise*` の組み込み関数が無い。
macOS の desktop GLSL 330 では `vec2 noise2(genType)` が予約済みで、そのまま移植すると

```
ERROR: Return type in redeclared function 'noise2' differs from previous declaration
ERROR: Incompatible types (float and vec2) in assignment
```

`vnoise` に改名して解決。**同じ GLSL でもプロファイルで組み込み関数の集合が違う。**
WebGL からの移植では最初に疑う場所。

## 2. フローを「1フレームあたり」で持つとフレームレート依存になる

`calcOpticalFlowFarneback` は 2 枚の画像間の変位を返す。これを画面幅で割って
「画面を1とした移動量」にしたが、これは *1フレームあたり* の量。

同じ人が同じ速さで手を振っても、**30 fps では 120 fps の 4 倍の値になる。**
絵の挙動がカメラのフレームレートで変わってしまう。`dt` で割って毎秒の量に正規化した。

解像度で割るところまでは自然に気づいたのに、時間で割ることを忘れていた。
「単位を書き出す」習慣があれば防げた種類のバグ。

## 3. 角度を `mix` してはいけない

筆の向きを「フローの方向」と「等深線の方向」で補間しようとして、最初は

```glsl
float ang = mix(contourA, flowA, w);   // 間違い
```

と書いた。角度は円周上の量なので、`0.1` と `3.0` (≈π) を混ぜると
本来ほぼ同じ向きなのに中間の `1.55` (直交) になる。

さらに筆の向きは**「方向」ではなく「軸」**で、180度回しても同じ筆。
2倍角ベクトル `(cos2θ, sin2θ)` に写してから混ぜ、`0.5*atan2` で戻すのが正しい。
構造テンソルで方位場を扱うときと同じ話。

## 4. 原典の移植で意味を取り違えた — 霞は「地物」にだけ掛かっていた

`ombrelle v11.3` の空気遠近:

```glsl
if(edge > 0.001){                  // ← 丘の草の内側だけ
  float distP = mix(2.0, 0.15, pow(depth, 0.7));
  g = mix(g, hazeG, 1.0 - exp(-distP*0.32));
}
```

`if` の中にあることに気づかず、カメラ版では全画面に掛けた。結果、空が灰紫に洗われた。

原典の `depth` は「丘の稜線から手前まで」の 0..1 で、**空はその範囲に含まれない**。
一方カメラ版の `depth=0` は空そのもの。同じ数式でも変数の意味する範囲が違う。

数式をコピーするときは、その数式が**どの領域で定義されていたか**まで見る必要があった。
遠側を圧縮して `uHaze` で調整できるようにした。

## 5. 「モデルを軽くする」前に「モデル以外」を測るべきだった

パラメータを 24.79 M → 0.97 M (25.6分の1) にしたのに、最初の実測は

```
teacher  total 21.8ms = pre 7.3 + forward 14.2 + readback 0.3
student  total 13.7ms = pre 7.0 + forward  6.5 + readback 0.2
```

forward は 2.2 倍速くなったのに合計は 1.6 倍。**前処理が 7 ms の固定費として残っていた。**
内訳を割ると `cv2.resize` の `INTER_AREA` で 1280x720 → 392x224 の縮小だけで **6.86 ms**。
student の forward より重い。

| 手法 | 時間 | |
|---|---|---|
| cv2 `INTER_AREA` | 6.86 ms | 品質は良いが遅い |
| cv2 `INTER_LINEAR` | 1.11 ms | 速いがエイリアスが出る |
| **GPU bilinear + antialias** | **1.27 ms** | 品質を保って 5.4 倍速 |

GPU に移して解決。**軽量化の話をするなら、まず何が律速か測る。**

副作用として学習/推論のドメイン一致が問題になった。`collect.py` が保存する画像は
`cv2.INTER_AREA` で縮小していたので、推論を GPU resize に変えると前処理がずれる。
`resize_uint8()` を共有して両方が同じ経路を通るようにし、データを取り直して再学習した。

## 6. 計測のばらつきを甘く見ていた

teacher の forward が 14.2 ms → 20.0 ms に「悪化」して見えたので、入力テンソルの
生成経路 (CPU 由来 / GPU 由来) が原因かと疑った。同じ入力テンソルを固定して測ると:

```
cpu-made input -> 15.77ms
gpu-made input -> 15.74ms
cpu-made input -> 18.31ms   ← 同じ条件で 2.5ms 動く
gpu-made input -> 15.97ms
```

入力経路は無関係で、単に GPU のクロック/熱状態で 16〜20 ms 揺れていた。

片方を n 回連続で測ってから他方を測ると、測定中のドリフトが片方だけに乗る。
**A/B を交互に回すペア設計**に直した (`bench_paired`)。

そこで見えたのは、median の差 (17.9 vs 7.0 ms) より **std の差 (5.6 vs 0.62)** の方が
実用上は重要だということ。リアルタイムループでは p90 が体験を決める。

## 7. フリッカ対策の EMA が、静止シーンでは逆効果だった

単眼深度は相対逆深度で絶対スケールを持たない。毎フレーム素の min-max 正規化をすると、
近い物が画面に入る/出るだけでレンジが跳ね、絵の側では

  * 筆のサイズが一斉に変わる
  * 彩度と霞の量が一斉に変わる

という形で「絵全体が呼吸する」。**深度の精度ではなく時間的一貫性の問題。**
min/max を非対称 EMA (広がる方向は速く α=0.35、縮む方向は遅く α=0.04) で追従させた。

ところが合成シーン (深度レンジがほぼ変わらない) で測ると:

| | 毎フレーム min-max | 非対称 EMA |
|---|---|---|
| teacher | 0.0072 | 0.0083 |
| student | 0.0045 | 0.0046 |

**EMA の方が悪い。** 追従ラグ自体がフレーム間の変化を生むため。
レンジが動かないシーンでは EMA に払うコストだけが残る。

対策が効く条件 (人が出入りしてレンジが跳ねる) を作らずに効果を測ろうとしたのが誤り。
実写での再測定が宿題。**「対策を入れた」ことと「対策が効いた」ことは別。**

## 8. 精度で劣る student の方が、深度が時間的に落ち着いていた

| | MAE (teacher基準) | 連続フレーム間の差 |
|---|---|---|
| teacher | — | 0.0072 |
| student | 0.0171 | **0.0045** |

小さいモデルは滑らかな関数なので入力の微小変化に反応しにくい。
この作品では深度は「絵のパラメータ」なので、1枚の精度よりフレーム間の落ち着きが
体験を支配する。**AbsRel や MAE が良い方が絵として良い、とは限らない。**

これは狙って作った結果ではなく、時間的一貫性を測ろうと思って測ったら出てきた。
指標を1つしか見ていたら見えなかった。

## 9. 誤差は輪郭に集中する — つまりオクルージョンに最も弱い

![compare](depth_compare_synth.png)

差分図 (右下) を見ると、誤差は物体の輪郭に集中している。student の出力解像度が
teacher の半分 (112x196 vs 224x392) であることも効いている。

  * 筆サイズ・彩度・霞 … 低周波の駆動 → student で十分
  * オクルージョンの境界 … 高周波 → student は弱い

同じ「深度」を2つの目的に使っているのに、要求される周波数帯が違う。
次の一手は勾配損失の重み上げ / 出力解像度 / エッジ考慮の refine。

## 10. データを「集めた枚数」と「実質のデータ量」は違う

60 fps で 1 分回せば 3600 枚だが、隣接フレームはほぼ同一画像。
そのまま学習すると実質的なデータは数十枚しかない。

前に採用したフレームとの平均絶対差が閾値未満なら捨てるようにした結果:

```
kept 700 / seen 3408 (skipped_near_duplicate 2708)
```

**8 割が近重複だった。**

同じ理由で train/val をランダム分割してはいけない。時間的に隣接するフレームが
val と train に分かれると、val に train のほぼ同じ画像が漏れてスコアが実力より
良く出る。連続ブロック単位で切った。

増強も左右反転だけに絞った。ラベルは「画像全体で頑健正規化した値」なので、
ランダムクロップするとその正規化が壊れる (切り取った領域の最遠点は元の最遠点ではない)。
測光系 (明度/コントラスト/彩度/ノイズ) は自由に掛けられる。

## 11. 単体ベンチだけでは「重いモデルが絵を遅くする」理由が説明できない

| | 単体レイテンシ | アプリ内 depth | 描画 fps | e2e |
|---|---|---|---|---|
| teacher | 17.9 ms | 35.0 ms | 52.9 | 36.3 ms |
| student | 7.0 ms | 22.6 ms | 134.6 | 22.2 ms |

アプリ内の推論時間は単体の 2 倍近い。描画と GPU を共有しているため。
逆に言えば、**重いモデルは深度の更新を遅らせるだけでなく、絵そのものを遅くする。**
単体 2.5x が描画 fps の 2.5x としてそのまま出た。

「その場で測る」ことを設計に組み込んだ (`d` キーで実行中に teacher↔student を
切り替えられる、終了時に深度の実効更新 Hz と捨てたフレーム数を出す) のが効いた。

## 12. 原典の「赤方向には決して届かない」は、変換の性質ではなく入力の性質だった

実写を初めて通したとき、肌がマゼンタに転んでノイズにしか見えなかった。原因は
原典の色彩分割をそのまま移植していたこと:

```glsl
// 三族は非対称: 青側は深く、黄側はささやき——赤方向には決して届かない
float fam  = floor(h1r*3.0) - 1.0;
float famG = ((fam < 0.0) ? -0.58 : fam*0.16) + (h2r - 0.5)*0.12;
col = hueRotate(col, famG);
```

固定の色相回転を掛けている。各対象の色相がどこへ飛ぶかを測った:

| 対象 | 元の色相 | 三族回転の行き先 | 最大ずれ |
|---|---|---|---|
| 草 (原典の対象) | 103.6° | 72.6° / 103.6° / 113.0° | 31.0° |
| **肌 (実写)** | 20.0° | **344.8°** / 20.0° / 28.4° | 35.2° |
| 木の机 | 24.8° | **350.0°** / 24.8° / 33.2° | 34.8° |

草は青緑〜緑〜黄の帯に収まる。コメント通りの設計。
ところが肌 (20°) に同じ -0.58 rad を掛けると **344.8° = マゼンタ**。0° を跨いでいる。

**「赤方向には決して届かない」という原典の不変条件は、変換が保証していたのではなく、
入力が緑だったから成立していただけ**だった。入力の色相が変われば即座に破れる。

4 の霞の件 (数式がどの領域で定義されていたか) とまったく同じ種類の間違いを、
別の場所でもう一度やっていた。**数式を移植するときは、その数式が暗黙に仮定している
入力の範囲まで持ってくる必要がある。**

### 直し方: 色相を回すのをやめる

印象派の色彩分割の一次原則は「光は暖色、影は寒色」で、これは元の色相に依存しない。
色相回転ではなく**色温度の軸**にずらす:

```glsl
float side = (h1r < 0.5) ? 0.0 : 1.0;              // 筆ごとに暖/寒を抽選
float bias = clamp((l0 - 0.45) * 1.6, -1.0, 1.0);  // 明るい筆ほど暖色に寄りやすい
vec3  tint = mix(COOL, WARM, clamp(side + 0.30*bias, 0.0, 1.0));
col *= mix(vec3(1.0), tint, amt);
col *= l0 / max(dot(col, LW), 1e-3);               // 輝度は保存(原典の思想は維持)
```

同じ測定を新方式で行うと、最大ずれは草 11.3° / 肌 5.3° / 机 0.8°。
色相を壊さずに暖寒だけが分かれる。

## 13. 筆の大きさを調整できるようにしていなかった

実写の初回で「全然綺麗じゃない」となったもう一つの理由。原典の筆のピッチ
`vec2(0.019, 0.0062)` は画面いっぱいの風景を想定した値で、1280x720 だと
長さ 7〜46 px・幅 2〜8 px。**カメラの近接被写体ではこれは「絵」ではなく
「ざらついた写真」に見える。**

霞・彩度・風・ぼかしは実行時に触れるようにしていたのに、
**「絵に見えるか」を最も強く決めるパラメータを固定値のままにしていた**のが設計の抜け。
`uBrush` を追加してピッチと楕円の軸を一括で倍率変更できるようにし、既定値を 1.8 にした。

## 14. 筆を大きくしたら、向きの場も同じだけ滑らかにしなければならなかった

`uBrush` を足して筆を 3〜5 倍にしたら、渦巻き(マーブル模様)と、物の輪郭の毛羽立ちが出た。

原因は構造的なもの。**筆の格子は画素ごとに向きで回転する。**
向きの場が「筆1本の大きさ」より速く変化すると、同じ一筆に属するはずの画素が
別々の格子を見て、格子が破れる。筆を大きくすることは、要求される向きの場の
滑らかさを同じ比率で厳しくすることだった。

対処は3つ:

1. **向きを決める場の空間周波数を筆の大きさで割る** — ノイズも深度勾配の差分幅も
   `bs` でスケールする。`fbm2(p*1.1/bs)`, `e = 2.0*bs/uRes.y`
2. **平らな面の向きをノイズで全周(2π)振らない** — 渦模様の正体。
   ゆるい斜めの筋目を基本にして ±0.8 rad に留める
3. **輪郭の向きは構造テンソルで平均する** — 深度が不連続な所では 1 点の勾配が
   数画素の間に大きく振れる。筆の footprint 内の 5 点で平均を取る。
   向きは軸なので **2 倍角ベクトルの和**で平均する (勾配ベクトルをそのまま平均すると
   符号が反転して打ち消し合う)。同時にテンソルの長さ/重みの和で「向きの揃い具合」が
   取れるので、輪郭が入り組んで打ち消し合う場所では輪郭に従わせない

3 の「2 倍角で平均する」は、3 の項で書いた `mixOrient` と同じ原理。
**方位場を扱うときは常にこれ**、という一般則として身についた。

## 15. 二値の暖寒分割は「絵」ではなく「塗り分け」に見える

12 で導入した暖寒の色彩分割を、最初は筆ごとに二値 (暖 or 寒) で振っていた。
強度を上げると橙と青の斑になり、ユーザーは分割を 0 に落とした。

直し方: 連続分布にして、振れ幅 `|u|` を強度に掛ける。
大半の筆はほとんど素のまま、少数だけが強く振れる。

```glsl
float u = h1r*2.0 - 1.0;                       // -1..1 連続
float w = clamp(0.5 + 0.5*u + 0.22*bias, 0.0, 1.0);
float amt = uSplit * (0.35 + 0.65*d) * abs(u); // |u| が小さい筆は素のまま
```

加えて、**実際の絵では隣り合う筆は色相より明度が違う**。
原典の明度ジッタは ±1.5% で、大きい筆にすると平らな面がのっぺり残った。
分割の強さに連動させて ±10% まで振るようにした。

## 16. どの楕円にも入らない画素が、格子に揃ったギザギザを作っていた

5x5 の近傍から楕円を1枚勝たせる仕組みで、どれにも入らない画素は
格子の素のセル中心に落ちていた。原典の細かい筆では見えなかったが、
筆を大きくすると**格子に揃った不連続 = 櫛状のギザギザした縁**になる。

最も近い楕円 (正規化距離 q2 が最小のもの) を控えに取り、隙間はそれで埋めた。

## 17. 「黒を使わない」を「暗い値を使わない」と取り違えて、絵が褪せていた

実写のスイープを並べて初めて分かった。紙も机も中間調に潰れ、元写真にあった
黒が全部消えていた。原因は `grade()`:

```glsl
vec3 SHADOW_V = vec3(0.30, 0.32, 0.48);   // 輝度 0.33
c = mix(c, mix(c, SHADOW_V, 0.60), sh);   // 暗部をこれと**混色**
```

輝度 0.33 の色と混ぜているので、輝度 0.15 の暗部は 0.26 まで**持ち上がる**。
明部も同様に 0.95 側へ寄せていたので、上下から圧縮されて褪色した。

印象派の原則は**「黒い絵具を使わない」であって「暗い値を使わない」ではない**。
モネの暗部は明るい灰色ではなく、深い青紫や深緑で、**暗くて彩度が高い**。

混色をやめ、色を**掛けてから輝度を元に戻す**方式にした。色相だけが振れて明度は動かない。
ついでに眠い写真に対して軽い S 字を掛け、値の構造をむしろ強めるようにした。

```glsl
vec3 t = mix(vec3(1.0), SHADOW_T, sh*0.60);
t = mix(t, LIGHT_T, hi*0.38);
c *= t;
c *= l / max(dot(c, LW), 1e-3);   // 輝度は保存
```

12 の色彩分割で「輝度を保存して色相だけ振る」を実装したのに、
すぐ上の grade() で同じ原則を破っていた。**同じ設計原則を全ての段に通す**べきだった。

## 18. 照明の色かぶりの上に暖色を重ねていた

17 を直したら今度は白い紙が黄色くなった。元写真が電球色の部屋で撮られていて、
**入力が既に暖色に転んでいる**ところへ暖色グレーディングを重ね、
さらに彩度で増幅していた。

絵の色は「影は寒色・光は暖色」という**相対的な**決め方をしている。
その相対の基準が照明で動くなら、先に基準を固定しないと法則が成立しない。

グレーワールド (シーンの平均は無彩色) で色かぶりを外してから絵の色を決めるようにした。
完全にではなく 75% だけ適用する — 画面が単色で埋まる場面 (芝生一面など) で
過補正になるため。

これは意匠のためだけの処理ではない。**照明条件が変わっても同じ絵の法則が成立する**
というロバスト性そのもの。

実写の測定値: 電球色の机の写真で gain = (1.041, 0.995, 0.917)。

## 19. 意匠を「並べて比べる」道具を先に作るべきだった

パラメータを 1 つずつ変えて実行し直し、記憶で比べていた。判断がぶれるし遅い。
`tools/sweep.py` で同じ画に複数の組を描いて 1 枚のコンタクトシートにしたら、
17 の褪色も 18 の黄変も**一目で**分かった。

絵に関する判断は「見て決める」しかないが、**見比べられる形にする**ところは
自動化できる。ここに手を抜いていた。

## 20. 彩度が二重に掛かっていた

人物を通したら肌が桃色に転んだ。マゼンタ (12) とは別の原因で、今度は単純な重複:

  * `grade()` で全体に `uChroma` = 1.35
  * 筆触パスで原典の `satG` = 1.18 + 0.28*depth、顔は depth≈1 なので 1.46

**掛け算で約 2.0 倍。** 肌を 2 倍彩度にすれば桃色になる。

原典に `uChroma` は無く、`satG` だけだった。カメラの写真は彩度が低いので全体の
持ち上げを足したが、既存の depth 変調と重なることを見ていなかった。
`satG = uChroma * (0.92 + 0.20*d)` にして、彩度を決める場所を一箇所に統合した。

**同じ量を 2 箇所で触っていないか**は、パラメータを追加するたびに確認すべきだった。

## 21. 良い入力が来て初めて、設計が要求していたものが分かる

机の写真では深度がほぼ平坦で、この作品の仕組みの半分 (手前ほど大きい筆、
奥ほど霞む、オクルージョン) が働いていなかった。人物が入った途端に

  * 顔が最も手前 → 大きく彩度の高い筆
  * 天井が奥へ抜ける → 細かく霞む筆
  * シルエットが明瞭 → 等深線に沿った筆が輪郭をなぞる

が全部同時に効いた。**「絵が綺麗じゃない」の原因の一部は被写体だった。**
深度を絵のパラメータにする設計を選んだ以上、深度が縮退した被写体では
設計の主張そのものが検証できない。

## 22. 色彩分割を「本物」にする — 平均が元の色に戻ることが定義

12 で固定色相回転を捨てて暖寒の振り分けにしたが、あれは色彩分割ではなく
単なる色温度のばらつきだった。原典のコメントは設計意図を正しく書いていた:

> 色彩分割: 草は三族に量子化(青緑/緑/黄——**緑を成分に分解**)

色彩分割の定義は「色を成分に分解して隣り合う筆に置き、**目の中で混ぜる**」こと。
要点は **平均すると元の色に戻る**ことで、その結果 **各筆は元より彩度が高くなる**。
これが「絵具を混ぜるより明るく見える」理由 — 混色は彩度を落とすが、並置は落とさない。

輝度を抜いた対立色平面で色度ベクトルを ±Δ 回すと、2 つの平均は cos(Δ) 倍に縮む。
だから各筆を **1/cos(Δ) 倍**に伸ばしておけば平均が厳密に元へ戻る。

```glsl
vec3 divide(vec3 c, float ang, float sat){
  float Y = dot(c, LW);
  vec2 v = vec2(c.r - Y, c.b - Y);          // 対立色平面の色度ベクトル
  float ca = cos(ang), sa = sin(ang);
  v = vec2(ca*v.x - sa*v.y, sa*v.x + ca*v.y) * sat;
  float R = Y + v.x, B = Y + v.y;
  float G = (Y - LW.r*R - LW.b*B) / LW.g;   // 輝度は定義から保存される
  return vec3(R, G, B);
}
```

数値で確認 (誤差は倍精度の丸め):

| 対象 | Δ | 平均の誤差 | 各筆の彩度 | 輝度の誤差 |
|---|---|---|---|---|
| 肌 | 17° | 0 | 1.086x | 0 |
| 肌 | 34° | 0 | 1.304x | 0 |
| 肌 | 52° | 0 | 1.775x | 0 |
| 草 | 34° | 1.1e-16 | 1.129x | 0 |
| 空 | 34° | 1.1e-16 | 1.282x | 0 |

どちらの側を引くかは輝度で偏らせる (明るい筆は暖かい側、暗い筆は冷たい側)。
これが原典の「三族は非対称: 青側は深く、黄側はささやき」の一般化にあたる。
原典は対象が緑だったので、その非対称性を固定角で書き下せた。

## 23. 色彩分割の強さと筆の大きさはトレードオフだった

分割を強くすると色ノイズに見える。調整の問題ではなく物理:
**光学混合は「筆が目の中で混ざるほど小さい」ことが前提**。
スーラは点、モネは大きめの筆で弱い分割 — 画法の違いはここに由来する。

実写で確認: `brush=0.6 split=0.85` は揺らめきとして読めるが、
`brush=2.4 split=0.85` は色の斑になる。

そこで**分離角を筆の大きさに反比例させた**。こうすると `uSplit` は
「目に見える揺らめきの量」という、筆サイズに依らない意味を持つ。
筆を変えても分割を調整し直さなくてよくなった。

パラメータ同士に物理的な従属関係があるなら、それは実装側で吸収して、
**人が触るツマミは独立した意味を持たせる**べきだった。

## 24. 「色が足りない」は気のせいではなかった — 分割は彩度を増やさない

ユーザーから「モネ寄りでいいけど色が足りない気がする」と言われて測った。

| | 彩度 mean (CIELAB) | 色相の広がり | 使用色相ビン |
|---|---|---|---|
| 入力 (カメラ) | 25.4 | 13° | 6/36 |
| 出力 split=0.5 | **11.5** | 61° | 19/36 |

**色相の多様性は 3 倍以上になったのに、彩度は半分以下に落ちていた。**

理由は 2 つとも設計どおりの帰結:

1. **色彩分割は定義上、平均を保存する** (22)。だから彩度の総量は増えない。
   増えるのは種類だけ。「分割を強くすれば色が増える」は誤り。
2. **グレーワールド** (18) が照明の色かぶりを外す。入力の彩度 25.4 の大半は
   電球色の一様なかぶりで、それを外せば当然落ちる。これは正しい動作。

さらに構造的な限界があった。`divide()` は色度ベクトルを回す操作なので、
**中性色は回しても中性のまま**。白飛び気味の天井が画面の大半を占めるこの写真では、
**一番広い面積で分割が空振りしていた**。

対処は画法そのもの: 画家は白い壁を「暖色と寒色」で描く。
分割の前に、輝度に応じた色度を注入する (`inject()`)。

  * 明るい面 → 暖色側、暗い面 → 寒色側
  * 元の彩度が低いほど強く注入する
  * 中間調で最大 (実際の絵具も最高彩度は中間調にあり、白飛びと黒潰れでは落ちる)

結果:

| | 彩度 mean | 色相の広がり | 使用ビン |
|---|---|---|---|
| inject=0 chroma=1.25 | 11.5 | 61° | 19/36 |
| inject=0.18 chroma=1.5 | 16.1 | 56° | 20/36 |
| inject=0.30 chroma=1.75 | **21.5** | 54° | 18/36 |

入力の彩度 25.4 は **1 色のかぶり** (6 ビン)、出力の 21.5 は **18 色の広がり**。
同じ数字でも意味が違う。「色が多い」を測るには彩度だけでも色相数だけでも足りず、
両方を同時に見る必要があった。

**「気のせいですか」と聞かれたら測る。** 測れば原因まで一度に分かる。

## 25. 分割が二値だったので「緑と赤が同じ色ばかり」になっていた

ユーザーの指摘: 「緑と赤が強すぎて綺麗じゃない。この緑と赤の色が同じ色すぎる」。

実装を見たら二値だった:

```glsl
vec3 cP = divide(col, +dlt, sat);   // 全ての筆が同じ Δ
vec3 cM = divide(col, -dlt, sat);   // 符号だけが違う
col = (h1r < 0.5 + 0.30*bias) ? warmC : coolC;
```

**局所色ごとに色が 2 つしか現れない。** だから同じ緑と同じ赤が延々と繰り返される。
22 で「平均が戻る」ことばかり考えて、**何種類の色が出るか**を見ていなかった。

分離角を筆ごとに連続分布から引くように変更。θ を [-Δ, Δ] の一様分布から引くと
平均は sin(Δ)/Δ 倍に縮むので、**Δ/sin(Δ) 倍**に伸ばせば平均が厳密に元へ戻る
(二値の 1/cos(Δ) に対応する)。モンテカルロで確認済み。

同時に、輝度による暖寒の偏りを divide() から inject() へ移した。
divide 側で偏らせると平均が保存されず、色彩分割の定義から外れるため。
役割を分けた:

  * `inject()` … 「光は暖色・影は寒色」の法則。平均を動かしてよい(意図的な脚色)
  * `divide()` … 色彩分割そのもの。平均は厳密に保存する

注入の軸も筆ごとに ±0.45rad 散らした。単一の軸だと中性面が同じ 2 色の繰り返しになる。

## 26. 「同じ色すぎる」を測る指標を作り直した

最初に測った「局所タイルの色相ビン数」は 4.1 → 4.4 とほぼ動かず、
目で見て明らかな改善を捉えられなかった。分離角が 20° 程度だと、
二値でも連続でも占有するビン数は変わらないため。

**上位 2 色相ビンの占有率**に変えたら、指摘そのものが数字になった:

| | 上位2ビンの占有 | 色相エントロピー |
|---|---|---|
| 入力 (カメラ) | 97.2% | 0.58 bit |
| 二値の分割 | 67.3% | 2.09 bit |
| 連続分布 | 61.2% | 2.29 bit |

**「何種類あるか」ではなく「どれだけ 2 色に偏っているか」を測るべきだった。**
指摘の言葉 (「同じ色すぎる」) をそのまま指標に翻訳すれば一度で当たった。

## 27. 「強すぎる」と「同じ色すぎる」は同時に直せる

分割は平均を保存するので、**分離角を広げても色の総量は増えない**。
広げた分だけ彩度を下げれば、色の量は据え置きで種類だけ増える:

| | 彩度 mean | 上位2ビン | エントロピー |
|---|---|---|---|
| split=0.5 chroma=1.50 | 16.2 | 61.2% | 2.29 bit |
| **split=1.0 chroma=1.35** | **15.2** | **52.7%** | **2.61 bit** |
| split=1.6 chroma=1.20 | 14.5 | 48.7% | 2.81 bit |

平均保存という性質が、そのまま「色数と色の強さを独立に動かせる」という
操作性になっていた。設計の性質が使い勝手に効いた例。

## 28. 格子を筆の向きで回していたのが、輪郭の糸屑の原因だった

指摘: 「輪郭が覆えてなくて、肌色に見えるのが良くない」。拡大したら、髪と顔の
境界に**櫛状の細い糸屑**が出ていた。

原典は「筆の向きで座標系ごと回してから格子を切る」方式:

```glsl
vec2 s = vec2(dot(p, sdir), dot(p, perp));   // 向きで回した座標
vec2 base = floor(s/pitch);                  // その上で格子を切る
```

原典の向きの場は解析的で滑らかなのでこれで成立していた。
ところが**実測の深度から作った向きの場は輪郭で急回転する** (そこでは急回転が正しい)。
座標系ごと回すと、同じ一筆に属するはずの隣り合う画素が**別々の格子**を見て、
筆が細い糸屑に砕ける。

構造テンソルで向きの場を平滑化しても消えなかった。当然で、
**輪郭で速く変わること自体は正しい**からである。平滑化は症状を薄めるだけだった。

直し方は格子の側:

  * 格子は画面に固定する (等方、回さない)
  * **各セルの楕円だけを、そのセル中心で引いた向きで回す**

こうすると全画素が同じセル集合に同意するので、糸屑は**原理的に**起きない。
筆は依然として向きの場に沿う (向きはセルごとに引くため)。
代償は探索範囲で、回転楕円が縦横どちらにも伸びるので 5x5 → 7x7 に広げた。

**「滑らかにする」で消えない縞は、たいてい離散化の側に原因がある。**

## 29. 「同じ色すぎる」と「肌色に見える」は逆方向の要求だった

同じ指摘の後半、「肌色に見える」。画家は肌を肌色では描かない。
緑や紫を置いて、離れて見たときに肌に見えるようにする。

ところが 25 で入れた一様分布では届かない。Δ=35° 程度では橙のまわりを
うろうろするだけで、緑にも紫にも行かない。裾の重い分布 (θ = Δ·sign(u)·|u|^2.5) を
試すと確かに遠くへ届くが、今度は大半の筆が中央に集まって
**上位2ビンの占有が 52.7% → 60.0% と悪化**した。25 の指摘が戻ってしまう。

2 つの要求は逆を向いていた:

  * 「同じ色すぎる」 → 均等に散ってほしい (一様が有利)
  * 「肌色に見える」 → 遠くまで振り切ってほしい (裾が重い方が有利)

**混合分布**で両立させた:

  * 確率 1-R … θ ~ U(-Δ, Δ)     基調。均等に散らす
  * 確率 R   … θ ~ U(-Δf, Δf)   飛び道具。肌から緑や紫へ振り切る (Δf = 2.6Δ)

平均の縮みは一様分布の sinc の混合なので閉じた式で書ける:
`(1-R)·sin(Δ)/Δ + R·sin(Δf)/Δf`。逆数を掛ければ平均は厳密に元へ戻る。

| | 彩度 | 上位2ビン | エントロピー |
|---|---|---|---|
| 一様 split=1.0 | 15.2 | 52.7% | 2.61 bit |
| 裾の重い分布 split=0.9 | 15.2 | 60.0% | 2.35 bit |
| **混合 split=1.0** | **19.1** | **49.4%** | **2.79 bit** |

3 指標すべてで両方を上回った。R=0.26, Δ=1.0 のとき 15% の筆が 57° 以上ずれる。

**相反する 2 つの要求が来たとき、片方を選ぶ前に「両方を別々の成分が担当する」形を
探すべきだった。** 分布の形をパラメータではなく設計対象として扱ったら解けた。

## 30. 格子を固定したら 130fps → 21fps になった。犯人は atan だった

28 で格子を固定したのは正しかったが、代償があった。回転格子では向きを
**画素あたり 1 回**引けばよかったのに、固定格子では **セルごとに** 引く必要がある
(セル中心の向きで楕円を回すため)。7x7 = 49 回。130fps が **21fps** に落ちた。

段階的に潰した。各段で必ず測った:

| 手 | fps |
|---|---|
| 固定格子 7x7、向きをその場で計算 | 21 |
| + 向きの場を低解像度テクスチャに焼く (`angle.frag`) | 34 |
| + hash21 x6 → hash42 x2、早期足切り、7x7 → 5x5 | 36 |
| **+ atan をやめて半角公式で cos/sin を出す** | **294** |

**最後の一手だけで 8 倍。** 向きの場は 2 倍角ベクトル (cos2θ, sin2θ) で焼いてある
(角度を線形補間すると ±π で破綻するため)。それを使うのに

```glsl
float a = 0.5*atan(av.y, av.x);   // 角度に戻して
float c = cos(a), s = sin(a);     // また三角関数
```

としていた。セルあたり atan + cos + sin の 3 回、25 セルで 75 回。
半角公式なら atan も cos/sin も要らない:

```glsl
cos a = sqrt((1 + cos2a)/2)
sin a = sign(sin2a)·sqrt((1 - cos2a)/2)
```

sqrt 2 回で済む。**2 倍角で持っているものを、わざわざ角度に戻していた。**
表現を選んだ時点で計算が要らなくなっていたのに、それに気づかず往復していた。

`hash42` 化や 7x7 → 5x5 は「効きそう」に見えて 36fps 止まりだった。
**当たりをつけて潰すのではなく、1 手ずつ測る**のが結局速い。

### 落とし穴: 比較条件を揃えていなかった

最適化の前後で絵が変わったように見えて焦ったが、片方が `--depth teacher`、
もう片方が `--depth off` (既定) だった。**深度が違うだけ**で、最適化とは無関係。
条件を揃えたら差は筆の密度だけ (ピッチを 0.013 → 0.0175 に変えたため) で、
向きの場も色も同一だった。

6 で「A/B は交互に測る」と書いておきながら、画の比較では条件を揃え損ねた。

## 31. 「背景によって肌が浮く」— 自然の彩度比をそのまま写していた

指摘: 「背景の色によっていい感じな場合と、肌色が浮いている場合がある」。
白い壁を背景にした写真で測ると、**入力の顔/壁の彩度比は 4.07 倍**あった。

私は彩度を線形ゲイン (`satG = uChroma*(0.92+0.20d)`) で掛けていた。
線形なら比は保存される。つまり **4 倍の比がそのまま出力に残る**。
背景が有彩色の場面ではたまたま比が小さいので「いい感じ」に見え、
白い壁だと肌だけが浮く。**場面によって当たり外れが出るのは、
比を制御していなかったから**だった。

絵具には最高彩度がある。画家は自然の彩度をそのまま写さず、**パレットの範囲へ
圧縮する**。低い彩度は持ち上げ、高い彩度は抑える。線形ゲインをやめて
コンパンダに置き換えた:

```glsl
Cn = CREF * pow(C/CREF, 0.60) * level;   // 指数 <1 で圧縮
Cn = min(Cn, CREF*2.2);                  // 絵具の上限
```

顔/壁の彩度比 **4.07 倍 → 1.65 倍**。3 枚の異なる写真 (白い壁 / 暗い天井 / 机) に
同じ設定を当てて、出力の彩度 mean が 19.9〜24.1 に収まることも確認した。

## 32. 平均保存は「平均」しか保証しない — 個々の筆に天井が要る

同じ写真で最初に出たのは**蛍光の虹色**だった。原因は 2 つの積:

  * 混合分布の飛び道具が Δf = 2.6Δ = 149° (ほぼ補色) まで振れる
  * 色彩分割の彩度補正 1/shrink = 1.67 倍が掛かる

肌は元の彩度が 31 と高い。そこへ 1.67 倍と補色回転が乗ればネオンになる。

**22 で「平均が元に戻る」ことを確認して満足していたが、平均が正しくても
個々の筆が絵具の範囲を超えうる。** 分割の後にもう一度だけ天井を当てるようにした
(`ceilChroma`)。飛び道具も Δf ≤ 1.25rad (72°)、割合 R も 26% → 14% に下げた。
顔のように見慣れた色の面では、緑の筆が 26% あると面全体がオリーブに見える。

## 33. 順序が結果を決めた — パレットを先に決めてから分割する

天井を付けても顔が緑と桃色の斑のままだった。処理の順序が
`inject → divide → compand` になっていたためで、
**高彩度の肌の上で色相を大きく振ってから抑えていた**。
振った後で彩度を落としても、色相の斑は残る。

順序を入れ替えた:

```
inject  … 中性面に色を入れる
compand … パレットの水準と圧縮を決める(ここで画面全体の彩度がほぼ揃う)
divide  … その水準のまま色相だけ散らす
ceil    … 分割の彩度補正が天井を超えた分だけ戻す
```

同じ関数の組み合わせでも、順序を変えただけで結果が変わった。
**「何をするか」だけでなく「どの順でするか」が設計だった。**

## 34. ワーカースレッドが黙って死ぬ設計になっていた

合成を入れた後、student 深度で `depth_updates=0.0Hz / dropped=223` になった。
直接呼ぶと動くのにワーカー経由では結果が 1 つも出ない。

Python はスレッド内の例外でそのスレッドだけを静かに終わらせる。この設計では
**ワーカーが死んでも描画は前回の深度を使い続ける**ので、絵は普通に出続ける。
「動いているように見えるが深度が更新されていない」状態に気づく手段が無かった。

`_loop` を try で包んで、落ちた事実と traceback を必ず記録・表示するようにした
(深度・セグメンテーションの両方)。

なお**今回の症状の原因は例外ではなかった**。ハンドラを入れても何も出ず、
2 回目以降は正常に 25.9Hz で回った。おそらく MPS の初回シェーダコンパイルで、
最初の 1 回だけ推論が極端に遅かった (Metal のパイプラインキャッシュが温まると解消)。
つまり**入れたハンドラはこのバグを直していない**。それでも入れる価値はある —
「静かに死ぬ経路がある」こと自体が設計の穴で、次に本当に落ちたときに分かる。

「対策を入れた」と「対策が効いた」は別、というのは 7 でも書いた。今回は
**原因が別だったのに直ったように見えた**ケースで、より紛らわしい。

## 35. 「背景が背景に見える」— 手前に何も無かった

指摘: 「まだ背景が背景！って感じ。小物置いたり、前後関係を作って、絵画と人を
同じ世界に入れたい」。

**書き割りと空間の差は、人物より手前に何かがあるかどうか**だった。
それまで描いていたものは丘も空も草も全部人物より奥で、人物は常に最前面。
どれだけ絵として綺麗でも「背景の前に立っている」にしかならない。

3 つ入れた:

  * **深度テストによる合成**。`mix(scene, person, matte)` をやめ、
    `matte × (風景の深度 < 人物の深度)` で決める。これだけで画面下の近い草が
    人物の足元を隠し、「草の前」から「草の中」になる
  * **中景の茎**。x 位置と深度を固定した 6 本。深度が人物より大きい茎は自動で手前、
    小さい茎は自動で奥。人が左右に動けば茎の間を抜ける。マスクは要らない
  * **接地の影**。人物の真上にマットがある地面を沈める。
    足元に影が無いと、前後関係を作っても figure が浮いたままになる

検証: `stand` (人物の立つ深度) を 0.45 と 0.95 で描き比べると、
深度 0.90 の茎が前者では人物の手前を通り、後者では人物に隠れる。

## 36. ワーカースレッドを 2 本にしたらアプリが間欠的にハングした

合成のために人物セグメンテーションを別スレッドで足したところ、アプリが
時々終了しなくなった。まず**発生率を測った** (同条件で 4 回ずつ):

| 構成 | 正常 | 深度が止まる | ハング |
|---|---|---|---|
| ワーカー1本 (深度のみ) | 4/4 | 0 | 0 |
| ワーカー1本 (セグのみ) | 4/4 | 0 | 0 |
| **ワーカー2本 (深度+セグ)** | **1/4** | 1/4 | **2/4** |

**torch-MPS の推論スレッドを 2 本、OpenGL のメインスレッドと並行させると壊れる。**
macOS では OpenGL も Metal の上で動くので、3 つの経路が同じ GPU を奪い合う。

深度とマットは同じフレームから作られ同じ合成に食われるので、1 本のスレッドで
順に実行するようにした (`ombrelle/vision.py`)。直列化のコストは 19.6 + 8.3 ≒ 28ms
だが、もともと描画より遅い前提の設計なので影響しない。

**統合後: 8 回中 8 回とも正常。**

### 先に立てた仮説は間違っていた

最初は「描画が速すぎて (115fps)、依存している推論を GPU から締め出している」と考え、
描画に上限を設けた。40fps では確かに直ったように見えた。

ところが**無制限 (120fps) でも正常に動く回があった**。仮説が正しければ起きないはずで、
そこで初めて「間欠的な現象を 1 回の観測で判断していた」と気づいた。
発生率を数えて初めて、真因がワーカーの本数だと分かった。

**間欠的なバグに対して「直った気がする」は証拠にならない。** 回数を数えるべきだった。
7 (EMA) でも同じことを書いたが、あのときは効果の測定、今回は**原因の同定**で同じ失敗をした。

## 37. 色相の振れ幅を全色相に一律で掛けていた — 肌は「記憶色」だった

指摘: 「肌色に緑使うのが気持ち悪いかも」。

29 で「画家は肌を肌色では描かない」として、少数の筆を緑や紫まで振り切るように
した。草や壁ではこれが効いていた。**肌だけが気持ち悪い。**

理由は美的な好みではなく知覚の非対称性で、**肌は記憶色 (memory color)** である。
人は見慣れた対象の色ズレに極端に敏感で、放送機器に肌色補正の回路が入っているのも
そのため。同じ振れ幅でも、草なら「豊か」に、肌なら「不快」になる。

**振れ幅を全色相に一律で掛けていたのが誤りだった。** 対立色平面での角度を測ると:

| 対象 | 角度 |
|---|---|
| 肌 (明) | -0.77 rad |
| 肌 (暗) | -0.72 rad |
| 木 | -0.87 rad |
| 白壁 | -1.44 rad |
| 草 | -2.11 rad |
| 空 | +2.04 rad |

肌と木は近いが、草と空は十分離れている。**肌の周りだけ狙って抑えられる。**
分離角に、肌の軌跡からの円周距離で減衰を掛けた (`uMemory`)。

選択的に効いているかを測った (顔の領域と壁の領域を分けて):

| | 顔の色相エントロピー | 壁の色相エントロピー | 壁の彩度 |
|---|---|---|---|
| 保護なし | 4.41 bit | 3.68 bit | 17.6 |
| 保護 0.9 | **4.00 bit** | 3.66 bit | 17.6 |

**肌の色相の散らばりだけ減り、壁は数値上まったく動いていない。**

一般則を作るときに「例外的に敏感な領域」を持たないと、平均的には正しくても
特定の対象で破綻する。ここでは対象の同定を**色相そのもの**でやったので、
セグメンテーションが無くても (合成しないモードでも) 効く。
